01Overview

AI shows up in WorkRadar in two layers, and the project treats them differently.

AI inside the product. Google Gemini writes the manager’s daily brief from the ranked snapshot. It runs through one serverless route on Vercel, so the API key never reaches the browser. It does not decide the ranking. A deterministic, explainable score does that, so every item can show why it is on the radar. Gemini answers under a JSON schema and its output is validated. If it fails, the app shows an on-device summary and says why.

AI used to build the product. Claude (Anthropic) was the build partner from brief to delivery. It framed the problem, drafted the PRD, set the visual direction, wrote the React app and the AI route, built the automated checks, generated the Figma file from the running app, and set up the Vercel deployment in my browser. I set the constraints and made the product calls: the Airtribe context, Gemini as the model provider, Vercel for hosting, and the scope. Every AI output went through a review pass before it shipped.

05Significant prompts

A · Daily brief

Where: api/_prompt.ts, sent by the /api/digest route

Model: Gemini 3.5 Flash-Lite (3.8 Flash fallback), temperature 0.3, responseMimeType: application/json + responseSchema

Design choices: facts-only rule, exact IDs so output can be validated, sentence-length caps so it fits the UI, and a fixed shape for each of the five sections.

You are WorkRadar, a chief-of-staff assistant for an engineering manager.
You receive a JSON snapshot of their team's work from Slack, Jira, GitHub and email.
Items are already ranked by a transparent priority score (0-100) and grouped into rings:
"now" (needs attention now), "today" and "later".
Write the manager's brief as JSON that matches the response schema.

Rules
- Use only facts in the snapshot. Never invent people, numbers, deadlines or items.
- Put the exact item "id" from the snapshot in every itemId field. Use team member ids for personId.
- Plain, specific language. No hype, no emojis, no exclamation marks.
- Each "why", "action" and "suggestion" is one sentence under 25 words.

Fields
- headline: 1-2 sentences. How many items need attention, how many people are blocked
  (and how many on the manager), and the one thing to start with and why.
- topWork: exactly 3 items the manager should personally act on today ... "why" is the concrete next step.
- happened: up to 6 notable events from happenedToday as short past-tense sentences.
- attention: every item in ring "now" (max 6), with why it matters now and the action to take.
- blocked: one entry per blocked person with personId, itemId, blockedOn, since and suggestion.

Prompting patterns that worked

  • Ask for a plan and questions first. “Prepare a list of what you need from me” turned a vague brief into concrete decisions before any code was written.
  • Give the model the business context. The prompt names the manager, the rings and what counts as needing attention, so the brief prioritises the way the team does.
  • Constrain output to the UI. Schema fields map one-to-one to UI slots, with word limits sized to the layout.
  • Make hallucinations detectable. Requiring exact item IDs means any invented item can be dropped automatically.
  • Pick the model by measuring, not by name. The bigger model looked like the obvious choice. Timing both on the live site flipped the default.
  • Review against screenshots, not code. Most quality issues (ranking surprises, copy, truncation) were only visible on the rendered screen.

07Key trade-offs

DecisionChosenInstead ofWhy, and what it costs
Who ranksDeterministic weighted score; AI for languageLLM ranks everythingExplainable, stable between refreshes, testable and free. It can’t pick up subtle context, so every factor is shown and the weights are adjustable.
Output formatJSON schema + validationFree-text summaryRenders into specific UI slots, links to real items and can be checked for invented IDs. Costs some expressiveness, mitigated by tight per-field instructions.
ArchitectureOne serverless route on VercelA workflow engine or a separate backendOne moving part to deploy and secure, free, and redeployed on every push. Scheduled jobs such as a morning digest would need a scheduler later.
ModelGemini 3.5 Flash-Lite, with 3.8 Flash as fallbackFlash or a Pro model as the defaultMeasured about 2 s against 35+ s. The brief summarises an already-ranked list, so the lighter model is enough. Nuance on long threads is weaker.
DeliveryStream the response at onceWait, then replySlow models can’t hit the edge time limit. The cost: errors travel inside a 200 response, so the client reads the body, not the status.
AvailabilityFlash-Lite → Flash → on-deviceSingle AI pathThe brief is never empty and failures are explained. The rare failure path waits for a second model.
Data sent to AITop 24 open items + blocked people + last 24hEvery raw threadFewer tokens, less private content leaving the app, more focused output. Low-ranked items can’t appear in the brief, which is acceptable by design.
DataMock workspace with timestamps relative to “now”Live OAuth connectorsAllowed by the brief. The demo always reads as “today” and is safe to share. Real-world noise and edge cases are untested until the pilot.
Design fileGenerated from the running app (DOM → Figma)Mockups drawn firstDesign and code never drift, and 15 states came cheaply. Layers are absolutely positioned rather than auto-layout components.
UI stackHand-written CSS tokens, no UI libraryComponent libraryA distinctive look, a small bundle (85 KB gzip JS) and full control of light and dark. More code to maintain; AI made it cheap to write.

Guardrails and how the AI is checked

  • Facts-only prompting with exact IDs, then validation that drops anything the snapshot can’t support.
  • Every score is explained by factor in the UI, so the manager can disagree and re-weight.
  • An engine label on every brief (Gemini or on-device), so users know what they’re reading.
  • Automated checks in CI (npm test): the expected top three (iPhone incident 97, PR #1284 93, LP-512 86), brief validation, search parsing, and the route’s fallback, origin and size rules.
  • Graceful failure: the outage banner hides a down source and explains the effect on ranking. AI failures show the reason, the on-device summary and Try again.
  • Secrets live only in Vercel’s environment variables. The browser never sees the key.

What I’d do next with AI

  • An eval set: 50 golden snapshots with expected top-3 lists, plus an LLM-as-judge faithfulness check on every brief, tracked weekly.
  • Live triage: once real connectors exist, Gemini reads Slack and email threads and sets priority, owner and next step.
  • Learned weights: tune the six weights per manager from opens, snoozes and reorders, keeping the explanation.
  • Reply drafts: Gemini drafts responses for “waiting on you” asks, sent only after the manager approves.
  • Write-back to Jira, GitHub and Slack, with an audit log and undo.
  • A privacy layer: redact personal data before anything is sent to Gemini, and keep message bodies for at most 7 days.
LessonThe most useful AI work wasn’t generating code. It was generating options and then critiquing the result from the user’s point of view, on real screenshots and on the live site. Measuring beat assuming: the “better” model was the wrong default.
